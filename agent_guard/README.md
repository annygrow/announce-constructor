# agent_guard — сетевой запрет активации для ИИ-агента в GetCourse

Запрещает агенту ровно два действия, оставляя всё остальное:
- рассылка «Готово к отправке»;
- процесс «Одобрить/активировать».

Принцип: режем конкретный HTTP-запрос на прокси. Через прокси идёт **любой** запрос из браузера — клик, сабмит формы, `fetch` из произвольного JS, — поэтому из браузера это не обойти (в т.ч. через `browser_run_code_unsafe`/`evaluate`).

## 1. Запуск прокси

```bash
pip install mitmproxy
mitmdump -s block_gc.py --listen-port 8080
```

Под другой аккаунт — поправить `HOSTS` в `block_gc.py`.

## 2. Направить браузер агента через прокси

mitmproxy расшифровывает HTTPS (иначе не прочитать POST-тело), поэтому браузер должен либо доверять его сертификату, либо игнорировать ошибки TLS.

**Вариант А (проще для автоматизации) — Playwright/Playwright-MCP с прокси + ignore-https-errors:**

Playwright MCP (`@playwright/mcp`) запускать с флагами:
```
--proxy-server http://127.0.0.1:8080  --ignore-https-errors
```
Или в коде Playwright:
```js
const ctx = await browser.newContext({
  proxy: { server: 'http://127.0.0.1:8080' },
  ignoreHTTPSErrors: true,
});
```

**Вариант Б (строже) — установить CA mitmproxy в профиль браузера:**
запустить mitmproxy, открыть `http://mitm.it`, поставить сертификат для нужной ОС/браузера. Тогда `ignore-https-errors` не нужен.

## 3. Проверка

1. Создать черновик рассылки и нажать «Сохранить» → проходит (200).
2. Нажать «Готово к отправке» → **403** (в логе mitmdump видно блок), рассылка остаётся черновиком.
3. Сохранить процесс с обычными настройками → проходит.
4. Поставить «Одобрено» и сохранить → **403**, процесс не активируется.

В окне `mitmdump` блок видно по строке ответа 403.

## 4. Закрыть обход мимо браузера (обязательно)

Прокси ловит только трафик браузера. Один теоретический обход — агент берёт cookie сессии и идёт `curl`'ом из Bash в обход браузера. Закрывается одним из:
- **egress-firewall**: с хоста агента наружу разрешён только сам прокси (исходящие 80/443 закрыты, весь HTTP(S) — через `127.0.0.1:8080`);
- запуск агента в **контейнере/VM**, где единственный выход в сеть — прокси;
- прокинуть и Bash-трафик через прокси: `HTTP_PROXY=http://127.0.0.1:8080 HTTPS_PROXY=http://127.0.0.1:8080`, а прямой egress закрыть firewall'ом.

Плюс по возможности у боевого агента **отключить `browser_run_code_unsafe` и `browser_evaluate`** и не давать инструментов с произвольным сетевым доступом — это убирает соблазн и лишние пути, хотя для этих двух эндпоинтов прокси и так держит.

## 5. Сигнатуры (что именно блокируется)

| Действие | Запрос | Признак | Что проходит |
|---|---|---|---|
| Рассылка «Готово к отправке» | POST `…/notifications/control/mailings/update/id/<ID>/…` | присутствует поле `ready` | «Сохранить» (без `ready`) |
| Процесс «Одобрить/активировать» | POST `…/pl/tasks/mission/update?id=<ID>` | `ParamsObject[approved]=1` | сохранение с `approved=0` |

## 6. Обслуживание / границы

- Это блок по сигнатуре запроса. Если GC переименует поле/эндпоинт — обновить сигнатуру: включить просмотр потоков `mitmproxy` (TUI), один раз воспроизвести действие, посмотреть реальный POST, поправить правило.
- Если у действия есть **другие пути** (например, «Готово к отправке» из списка рассылок или массовое действие) — поймать их так же и добавить правило. Текущие правила покрывают активацию из карточки рассылки и из формы процесса.
- Самый надёжный нижний слой всё равно — **урезанная роль робот-аккаунта** в GC для разделов целиком; прокси добивает точечные кнопки, которые роль не делит.
